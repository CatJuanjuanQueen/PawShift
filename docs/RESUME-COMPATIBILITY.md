# 0.3.3 旧暂停任务继续执行修复

在现有用户数据中确认：任务为 `PAUSED`，原 AGENT 执行为已结束的 `managed-sent`，但没有 `pausedTaskId` 和 `resumeTaskId` 设置。0.3.2 的继续逻辑只识别新版全局暂停保存的指针，因此把旧暂停任务误判成空队列。之前的真实测试只覆盖了新版暂停后再继续，未覆盖这组旧数据。

修复后的行为：

- 缺少恢复指针时，识别唯一一个有暂停执行记录的任务，并沿用原会话继续。草稿和已取消任务不会被启动。
- 如果有多个暂停任务，明确提示选择；队列和详情提供「继续此任务」，将指定任务送入完整执行管道，而非只修改入队状态。
- 对旧版遗留的工具运行标记，先读取原会话，核对原轮次终态与工具状态，再恢复。不能确认停止时保持暂停，不发送新轮次。
- 在发送轮次前恢复失败时，保留暂停状态和原会话，显示原因，可以直接重试。发送结果不确定时仍保留恢复锁。
- 界面显示待继续或正在恢复的任务标题；托盘操作打开任务队列并显示执行反馈。

新增回归覆盖旧版缺少指针、草稿和取消项、多暂停任务选择、恢复失败重试、旧工具标记核对，以及指定任务的界面命令。

`npm run test:resume` 使用隔离项目和数据库运行真实 AGENT。测试实际点击执行，在文件授权等待时暂停，关闭程序，移除恢复指针并加入旧工具标记，再重新打开程序点击继续。核对线程身份相同、新轮次身份不同、最终文件通过验收，并验证重启与原生桥接。对话框答案由显式测试模式提供，AGENT 与文件操作使用真实链路。报告见 `legacy-resume-check.json`。

仅只读检查了原用户数据库及原 AGENT 轮次；测试不会启动用户项目任务，也不修改原用户数据库。新版发布在 `release-webview2/PawShift-0.3.3/`，根目录启动文件与 `npm start` 已指向新版。
